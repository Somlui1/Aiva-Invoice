## 2. "ระบบหา field ไม่เจอ" ใน v5.5 จริง ๆ แล้วเกิดจาก 5 กลไกที่ต่างกันมาก

อ่านจากโค้ด (ไม่แก้) + ยืนยันด้วย payload จริงของรอบนี้ ลำดับเหตุการณ์คือ

```
single_pass._rf()      → ค่าทุก field ที่อ่านได้มาส่งด้วย agreement=False, confidence=None
                         ("one reader: agreement False -> the domain needs independent
                           evidence (arithmetic / Oracle) to accept it")
normalize._nfield()    → policy.confidence ของ key/money ตั้ง require_agreement: true
                         ถ้า agreement=False → ok=False, null_reason = CONFLICT_BETWEEN_SOURCES
                         ถ้า normalize แล้วตกกติกา → null_reason = INVALID_FORMAT:<REASON>
                         ถ้า raw ว่าง → null_reason = NOT_PRESENT
evidence.promote()     → กู้คืนได้เฉพาะ null_reason ∈ {CONFLICT_BETWEEN_SOURCES, LOW_CONFIDENCE}
                         โดย arithmetic ปิดยอด / เท่ากับค่า Oracle / ถูกคลุมด้วย customer_tax_id
rules.v01_required()   → ทุก field ที่ ok=False ใน required_fields + required_line_cells
                         + pages_complete + check_row_geometry_and_overlap()
                         → E01 (Medium = REVIEW) หรือ Low ถ้า miss ทั้งหมดคือ po_number และ Oracle ยืนยันได้
```

ดังนั้นคำว่า "หาไม่เจอ" ต้องแยกให้ออก 5 อย่าง:

| # | `null_reason` | ความหมายจริง | จำนวนใน 57 เอกสารที่ไม่ใช่ Auto Pass |
|---|---|---|---|
| 1 | `CONFLICT_BETWEEN_SOURCES` | **อ่านค่าได้และ normalize ได้** แต่ไม่เชื่อ เพราะ "ไม่มีผู้อ่านคนที่สอง" + ไม่มีหลักฐานอิสระมาช่วยยืนยัน (single-pass มี reader เดียว → ชื่อ reason นี้ *ไม่ใช่* ความขัดแย้งของสองแหล่งจริง) | 82 field-slot / **19 เอกสาร** |
| 2 | `NOT_PRESENT` | โมเดลตอบว่าไม่มีค่าในหน้า — บางกรณีไม่มีจริงบนกระดาษ บางกรณี **มีพิมพ์อยู่แต่ระบบอ่านไม่เจอ** (ต้องดูภาพ) | 78 field-slot / **19 เอกสาร** |
| 3 | `INVALID_FORMAT:*` | อ่านได้ แต่กติกาปฏิเสธ (`PO_NOT_8_DIGITS` 3, `TAX_ID_CHECKSUM` 2, `PO_NOT_NUMERIC` 1) | 6 field-slot / **6 เอกสาร** (36, 52, 68, 134, 175, 194) |
| 4 | `L*.bbox(UNGROUNDED_GEOMETRY)` / `L*.overlap(COLLISION_RATIO_*)` / `L*.order` | **ค่าครบทุกช่อง** แต่ "เรขาคณิตของบรรทัด" ไม่ผ่านกติกา `check_row_geometry_and_overlap` | 33 field-slot / **19 เอกสาร** |
| 5 | `pages_complete(false)` / `lines(NOT_PRESENT)` | อ่านไม่ครบทั้งฉบับ (เกิน `max_pages=12`) หรือ gate ตัดหน้า "ไม่ใช่ใบกำกับภาษี" ทิ้งทั้งเอกสาร | **13 + 7 เอกสาร** |

`item_code` อยู่ในกลุ่ม `optional` ของ `policy.yaml` จึง **ไม่มีผลต่อสถานะ** — รอบนี้เติมได้ 310/485 บรรทัด (63.9%) และ 77 เอกสารไม่มีเลย (ค่าที่โมเดลอ่านไม่ได้หรือไม่มีคอลัมน์ในกระดาษ)

## 3. สาเหตุใหญ่ที่สุดคือ "เรขาคณิตของบรรทัด" ไม่ใช่ OCR (19 เอกสาร / 43% ของที่ V-01 fail)

```python
if h <= 0 or (w / h) < 1.2:  errs.append(f"L{n}.bbox(UNGROUNDED_GEOMETRY)")   # บรรทัดต้อง "กว้างกว่าสูง"
...  if overlap_ratio > 0.50:  errs.append(f"L{n}.overlap(COLLISION_RATIO_…)")
```

**(ก) หน้าที่ถูกหมุน 90° — กล่องถูกต้องแต่กติกาผิด** (8 เอกสาร: 32, 36, 49, 59, 62, 64, 118, 119)

| DMS-62 / 64 | r=90 | 0.053 × 0.970 | 0.05 |

หลักฐานภาพ (MCP vision, `DMS-119_pdfspace_boxes.png`): *"the rectangles run **along** the direction of the printed text lines … in the sideways image each rectangle is a tall, narrow vertical strip; after the 90° clockwise rotation that strip becomes a long, thin horizontal bar"* → กล่อง **ครอบถูกรายการ** เพียงแต่ใน frame ก่อนหมุนมันมีลักษณะ "ตั้ง" เสมอ กติกา `w/h ≥ 1.2` จึงปฏิเสธทุกบรรทัดของทุกหน้าที่ถูกหมุน (ตรงกับ backlog B-2 ที่ว่าหน้าหมุนอยู่นอกกรอบการวัด)

**(ข) `overlap` บนหน้าตรง ๆ ที่ตารางแน่น** (9 เอกสาร: 26, 52, 132, 134, 153, 156, 178, 191, 202)

## 9. สรุปสาเหตุเชิงตัวเลข (เอกสารที่ V-01 fail = 44 ฉบับ)

1. **กติกาเรขาคณิตของบรรทัด** = ตัวบล็อกหลัก (19 เอกสาร / 43% ของ V-01 fail) และ 8 ในนั้นคือ **หน้าหมุน 90°** ที่กล่องถูกต้องโดยสัมพัทธ์
2. **ไม่มีผู้อ่านคนที่สอง** (single-pass) + หลักฐานอิสระไม่พอ → `CONFLICT_BETWEEN_SOURCES` 82 field-slot ใน 19 เอกสาร — ชื่อ reason ทำให้เข้าใจผิดว่าเป็นความขัดแย้งของสองแหล่ง
3. **ไม่มีใบรับใน Oracle** (11 ฉบับที่ query แล้วได้ 0 แถว) แต่สถานะออกมาเป็น E01 Medium ไม่ใช่ E05 High เพราะ V-04 ถูก `halted_by=V-01` บังไว้
4. **กระดาษไม่มีค่าจริง** (qty/unit price ว่าง, buyer tax id ว่าง, ไม่มีบรรทัด VAT, ไม่มี PO) — ตรวจภาพแล้วยืนยัน 6+ ฉบับ → REVIEW กลุ่มนี้ "ถูกต้อง"
5. **OCR/format จริง** จำนวนน้อยแต่ชี้เป้าชัด: 1 tax id OCR ผิดหลัก (DMS-194), 1 tax id ที่กระดาษผิดจริง (DMS-68), PO ผิด label / กลืน 2 ค่า (DMS-52, 36, 175)
6. **ข้อจำกัด engine ที่มองเห็นชัดจากข้อมูลรอบนี้**: `max_pages=12` (DMS-40 13 หน้า, DMS-95 19 หน้า → ยอดรวมไม่ถูกอ่าน), PO ถูกบังคับ 8 หลัก (`po_and_release`), การเก็บ box ในหน้า-space ก่อนหมุนทำให้กติกา aspect ใช้ไม่ได้กับหน้าหมุน

## 10. ข้อจำกัดของการตรวจนี้ / สิ่งที่ยังสรุปไม่ได้

* โมเดล vision เป็น reasoning model ที่เผา token กับการคิด (8k/request) ทำให้ 4 ภาพถูกตัดจบ (`vision_batch*.md` มี note) — ผลที่อ้างในรายงานนี้ใช้เฉพาะภาพที่ตอบจบ
* ตรวจภาพแบบ "single observation ต่อเอกสาร" (noise ของโมเดล 15.9% ตาม R6-8) — ตัวเลขที่ควรเชื่อคือค่าที่ engine และ vision เห็นตรงกัน (เช่น DMS-68 tax id, DMS-120 PO) ไม่ใช่การอ่านครั้งเดียวของฝ่ายใดฝ่ายหนึ่ง
* DMS-205 ยังอ่านภาพไม่จบ (โมเดลวน) — อ้างว่าเป็น delivery note ไม่ได้จากรอบนี้
* DMS-24 มีเลขที่ซื้อ 2 ตัวพิมพ์อยู่ (`เลขที่สั่งซื้อ/ขาย 50688296`, `เลขที่ใบแจ้งซื้อ 42052615`) — ตัวไหนคือ PO ที่ถูกต้องเป็น **นโยบาย owner** ไม่ใช่สิ่งที่ข้อมูลนี้ตัดสินได้
* ชุดเอกสารซ้ำ: DMS-118 (ใบกำกับภาษี) กับ DMS-123 (ใบส่งสินค้าของยอดเดียวกัน 19,281.40) เป็นคนละ DMS id — ต้องตัดสินว่าจะ dedupe/ผูกคู่กันอย่างไร
